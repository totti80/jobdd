# D-001｜HMを人材紹介業務支援SaaSとして検討

**時期：** 2026年6月〜7月  
**Status：** 過去の意思決定

## それまでの状態

勤務先で人材紹介の新規事業を検討した経験から、人材紹介事業への関心を持っていた。

ハローワークに大量の求人・求職者データが存在し、一定条件を満たした職業紹介事業者が利用できる仕組みを知った。

## 当時の仮説

中小人材紹介会社は、

**求人と求職者を効率的に照合すること**

に大きなPainを持っているのではないか。

## 意思決定

ハローワーク等のデータを利用して、

- 求人検索
- 求人保存
- 求職者管理
- 求人と求職者のマッチング
- 紹介業務効率化

を支援するサービス「HM」を開発する。

## 結果

実際にWebアプリとしてプロトタイプを開発した。

**時期：** 2026年8月  
**Status：** 確定

## それまでの状態

卒業制作としてHMを継続開発する方針だった。

## 新しく得られた情報

**求人探索の効率化よりも、良い求職者の獲得**

# D-011｜公平な比較市場をJobDDの設計原則とする

**日付：** 2026-08-20  
**Status：** 現在採用中

## それまでの状態

JobDDでは、課金有無をScoreや比較順位へ反映せず、未提携会社も比較対象に含める構想を採用していた。

一方で、JobDDが特に価値を提供したい人材紹介会社像については明確に定義していなかった。

## 新しく得られた情報・議論

大規模な自社集客基盤を持つ事業者に対し、専門性は高いが独自の大規模集客基盤を持たない中小・専門特化型人材紹介会社は、求職者から発見される機会そのものに課題を持つ可能性がある。

ただし、中小企業を恣意的に優遇すると、求職者のDecision SupportというJobDDの思想と矛盾する。

## 意思決定

JobDDは、

**大手・中小を会社規模で有利不利にせず、求職者との適合性で公平に比較する。**

会社規模・知名度・広告力そのものはJobDD Scoreの直接的な評価軸としない。

中小人材紹介会社を勝たせるための補正は行わない。

その代わり、専門性・職種・業界・地域・経験層・求人適合等によって、知名度の低い紹介会社でも求職者に適合すれば高く評価される仕組みを目指す。

## 判断理由

求職者にとってのBetter Choiceを優先しながら、結果として専門特化型・中小人材紹介会社にも「広告力ではなく適合性で選ばれる機会」を提供できるため。

## 影響範囲

- JobDDのVISION
- JobDD Score
- 比較画面
- B2B営業メッセージ
- 将来の紹介会社ターゲティング

## 今後の検証事項

- 中小・専門特化型人材紹介会社がこの価値に反応するか
- 高適合リードに支払意思があるか
- 求職者が知名度より適合理由を重視するか

# D-012｜JobDD Scoreのデータ・採点原則を定める

**日付：** 2026-08-20  
**Status：** 現在採用中（具体配点は未確定）

## それまでの状態

JobDD Scoreは、説明可能なスコアとし、MVPではルールベース＋根拠表示から開始する方針だった。

しかし、どの情報源を採点へ利用し、企業公式サイトの定性的表現をどのように扱うかは未整理だった。

## 新しく得られた情報

厚生労働省「人材サービス総合サイト」では、職業紹介事業者について、許可情報、取扱職種・地域、就職者数等の公的・構造化された情報が確認できる。

一方、企業公式サイトには職種・地域・公開求人・年収帯等の有用な情報が存在するが、「○○に強い」「手厚い支援」等の自己申告的表現をそのまま採点すると、マーケティング表現の巧拙によってScoreがぶれる可能性がある。

## 意思決定

JobDD Scoreは、

**公的・客観的・検証可能な情報を採点の基礎とする。**

企業公式サイトも利用するが、原則として、

- 公開求人件数
- 対応職種
- 対応業界
- 対応地域
- 年収帯
- 拠点
- その他第三者が確認可能な事実

を採点対象とする。

「製造業に強い」「手厚い支援」等の定性的・自己申告的表現は、その文言だけでは原則として直接加点しない。

また、会社規模、知名度、JobDDへの課金有無・提携有無はScoreへ直接反映しない。

## HYPOTHESIS

主要評価軸候補は、

- 職種適合
- 業界適合
- 地域適合
- 経験レベル適合
- 年収レンジ適合
- 現在求人との適合

とする。

具体的な配点は求職者インタビューと実データによる採点シミュレーション後に決定する。

また、Scoreとは別に算定根拠の強さを示すEvidence Levelを設けることを検討する。

## 判断理由

- Scoreの再現性を高めるため
- 企業のマーケティング表現による採点ブレを抑えるため
- 大手・中小を同じ評価基準で比較するため
- 「なぜこのScoreなのか」を求職者へ説明できるようにするため
- RecommendではなくDecision Supportという思想を維持するため

## 影響範囲

- JobDD Score
- データ収集
- 比較画面
- MVP設計
- 将来のデータ更新方法

## 今後の検証事項

- 具体配点
- 公開情報から安定して取得可能な項目
- 求職者が重視する評価軸
- 事業規模に比例しやすい数値の正規化方法
- Evidence Levelの有用性

# D-013｜JobDD / JobDDDを統合し、応募経路Decision Supportとしてモックを制作

**日付：** 2026-08-27  
**Status：** 現在採用中／モック検証前

## それまでの状態

JobDDは、

**求職者が自分に合う人材紹介会社を登録前に比較するサービス**

として検討していた。

一方、別案としてJobDDDを設け、

**求職者が企業へ直接応募するルート**

を強くする案も検討していた。

そのため、

- Agent比較を中心とするJobDD
- Direct応募を中心とするJobDDD

のどちらを採用するかに迷いが生じていた。

## 新しく得られた情報

東京科学大学の公開求人を調査したところ、一部募集では、

**ビズリーチ上の応募＋大学指定の提出手続き**

が必要なケースを確認した。

この事例から、

**Directが常に最適・正式な応募経路とは限らない**

ことを実体験として確認した。

また、ユーザー自身が広告を見た際に、

**「媒体へそのまま登録する」のではなく、AIへ最適な応募経路を調べさせる**

という行動を自然に取った。

## 意思決定

JobDDとJobDDDを別々に制作せず、

**Direct / Agent / Platform をJobDD内の選択肢として統合する。**

卒業制作モックは統合版1本で制作する。

## 新しい基本構造

### 第1階層

- Direct
- Agent
- Platform

を比較する。

### 第2階層

Agentが有力な場合のみ、

複数の人材紹介会社をJobDD Score等で比較する。

## 判断理由

- Directを無条件に優先することが求職者利益とは限らないため
- JobDD / JobDDDを別サービスにする必要が薄れたため
- 従来の人材紹介会社比較資産を捨てずに活かせるため
- 「RecommendではなくDecision Support」と整合するため
- JobDDが特定の応募経路の販売者ではなく、比較のメタレイヤーになれるため

## 影響範囲

- JobDDの定義
- MVP
- 画面設計
- インタビュー仮説
- North Star
- JobDD Scoreの位置づけ
- 競合定義
- 将来のマネタイズ設計

## 今後の検証事項

- 求職者が応募経路比較にPainを持つか
- Direct / Agent / Platformの比較軸
- 比較結果が実際の行動を変えるか
- Agent比較が第2階層として必要か
- 東京科学大学のようなケースが他求人でもどの程度あるか

# D-016｜課金有無と応募経路判定を分離する

**日付：** 2026-08-27  
**Status：** 現在採用中

## 背景

企業側が継続契約しなければ以後紹介しない、という案を検討した。

しかし、未契約企業へのDirect応募が求職者にとって最適な場合、その企業を比較対象から外すと、

**JobDDの中立性・Decision Support思想と矛盾する。**

## 意思決定

企業・人材紹介会社・Platformの課金有無によって、

- 比較対象
- JobDD Score
- 応募経路判定
- 表示順位

を変更しない。

未契約企業でも、公開情報上その経路が有力であれば候補として表示する。

## 収益化の考え方

課金対象は、

**比較結果への掲載権**

ではなく、

- JobDD経由の接続機能
- 継続的な高適合リード
- 追加的なB2B機能

等と分離して検討する。

## 判断理由

求職者にとってのBetter Choiceを最優先し、JobDDの信頼性を守るため。

# D-018｜AI時代の模倣耐性をJobDDの設計原則として採用

**日付：** 2026-08-28  
**Status：** 現在採用中

## それまでの状態

JobDDでは、

- RecommendではなくDecision Support
- 説明可能なJobDD Score
- 公的・客観的・検証可能なデータを優先
- 課金有無と比較結果を分離

という設計原則を持っていた。

一方で、AI時代にJobDDがどのような資産を積み上げ、模倣されても価値を維持するかは明文化していなかった。

## 新しく得られた情報

那珂慎二氏のコラム
「そのアプリ、なぜあなたが作る必要があるのか
――AI時代に『模倣されないサービス』をつくるための思考法」
から、以下の観点を得た。

- AI利用そのものは差別化になりにくい
- AIへ判断を丸投げすると独自判断が平均化しやすい
- 独自データ、体験設計、業界知識、信頼・関係性が模倣されにくい資産になる
- 「作れること」より「何を作るべきか分かっていること」が重要
- 1年後に何が積み上がるかを設計する

## 意思決定

JobDDでは、

**AIを差別化の中心に置かず、独自の判断ロジックと、利用・検証を通じて積み上がる資産を重視する。**

特にJobDD Scoreは、汎用AIに採点判断を丸投げせず、

- 評価軸
- 判定ルール
- 重み付け
- N/A処理
- Evidence Level
- 求職者属性による評価変化

を、検証を通じてJobDD独自の判断ロジックとして育てる。

また、将来的には適切な同意・プライバシー保護・法的整理を前提として、

- 求職者の比較行動

- 紹介会社選択
- 適合理由への反応
- 相談・応募・転職結果

等が蓄積され、JobDDのDecision Supportが改善する構造を目指す。

## 判断理由

AI APIや画面・コードは模倣されやすい一方、

- 実ユーザーから蓄積したデータ

- ユーザー観察から磨いた比較UX

- 求職者・紹介会社・専門家との信頼関係

は時間をかけて蓄積されるため。

また、この考え方はJobDDの

**RecommendではなくDecision Support**

という既存思想と整合する。

## HYPOTHESIS

JobDDが実際に利用されるようになれば、

**「公開情報だけの比較」から「実際の意思決定・行動・結果を反映した比較」へ進化し、時間差の資産を形成できる可能性がある。**

# D-024｜Slice 4のテストログ整理ルールを採用する

**日付：** 2026-08-30  
**Status：** 現在採用中

## それまでの状態

Slice 4としてinteraction_logsを実装し、results_viewed / evidence_opened / route_opened / route_selected / contact_clickedを保存できる状態になった。

一方、開発中のブラウザ再読み込みや操作テストによって大量のログが生成され、今後の求職者インタビューで得る実ユーザーログと混在する可能性が出てきた。

## 得られた情報

卒業制作MVPで重要なのは高度なログ管理機能を作ることではなく、求職者が実際に何を見て、どの根拠を確認し、どの応募経路を選び、外部行動へ進んだかを検証できることである。

また、現段階では開発ログと実ユーザーログを分離するためだけにis_testカラムや複雑なセッション管理を追加すると、Pain検証より実装作業が先行する。

## 意思決定

卒業制作MVPでは、interaction_logsについて以下の運用ルールを採用する。

1. 開発中に生成されたログはすべてテストログとして扱う。
2. 最初の求職者インタビュー直前に既存テストログを一度全削除し、その時点を検証開始ラインとする。
3. 検証開始後の実ユーザーログは原則削除せず、生ログを保持する。
4. ページ再読み込み等による重複は保存を許容し、分析時に必要に応じて重複除外する。
5. 経路の選び直しは削除せず、意思決定過程として保持する。
6. 検証開始後の開発確認は専用のテスト用user_query_idを使用し、分析時に除外する。
7. MVPではis_testカラム等の専用実装は追加しない。

## 判断理由

- 実ユーザーの行動データへ開発ログが混入することを防ぐため
- MVPで必要な検証精度を、追加実装を最小限にして確保できるため
- 再読み込みや選び直しを含む生ログを残すことで、後から分析方法を変更できるため
- ログ基盤の高度化より、求職者側Painの検証を優先するため

## 影響範囲

- interaction_logs運用
- 求職者インタビュー開始前の準備
- 行動データ分析
- 開発時の動作確認方法
- 将来のログ・プライバシー設計

## 今後の検証事項

- 重複除外の具体的な集計ルール
- session識別や匿名ユーザー識別の必要性
- is_testカラムが必要になる利用規模・運用条件
- ログ保持期間とプライバシー整理
- 行動ログがJobDDの最重要仮説検証にどこまで有効か

## 注意

この意思決定は、ログ取得を目的化するものではない。

最優先するのは、

**求職者がJobDDを使って比較材料を確認し、自分で応募経路を選ぶ行動が実際に起きるかを検証すること**

である。

# D-039｜経路別の外部データ取得戦略を採用する

**日付：** 2026-09-07  
**Status：** 現在採用中／一部実装・一部検証中

## それまでの状態

JobDDでは、Platform / Agent / Directの実データ取得を進めるため、Python Crawlerを共通基盤として整備していた。

## 新しく得られた情報

Careerjet Publisher APIについて実際に接続確認を行い、`機械設計 × 兵庫県 × 正社員` の検索に成功した。

APIは求人検索に必要な情報を返す一方、`user_ip` / `user_agent` / `Referer` 等のユーザー起点情報を要求する仕様であり、毎朝の無人定期Crawlerより、JobDD上の検索操作から呼び出すSearch APIとして扱う方が自然であることが分かった。

### Platform

- Careerjet APIを主系統候補として求人Discoveryに利用する
- Jooble APIを第2系統候補として検証する
- 単一APIへ依存しない
- APIで不足する媒体については、取得・保存・再利用条件を確認できたソースのみPython Crawler対象とする
- Platform APIは求人DBの大量複製ではなく、求人候補の発見に利用する

- Agent各社の全求人一括Crawlerを標準方式としない
- 厚労省等の公的・構造化Factを基礎情報として利用する
- Agent公式サイトから、会社概要・拠点・対応職種・対応業界等の検証可能なFactを確認する
- Platform等で発見した求人について、必要に応じてAgent公式サイト上の求人route・根拠URLを確認する
- 求人定期Crawlerは、robots.txt、利用規約、保存・再利用条件等を確認できたAgentだけ対象とする

### Direct

- 既存のD-038を維持する
- Platform / Agent / 公的求人等で求人を発見した後、企業公式採用ページへ逆引きする
- 同一・類似求人とDirect応募可否を確認し、確認できた場合にapplication_routesへDirect routeを追加する

## 技術上の責務分離

### Laravel

ユーザー起点のSearch APIを担当する。

候補：

- Careerjet
- Jooble
- 将来の公式求人検索API

定期Crawler、公式ページ調査、データ整形を担当する。

- Entity
- Job
- Fact

- 技術的取得可否と利用可否を分離するため
- Agent求人全文の大量保存を前提にしなくてもroute比較を成立させられるため
- Directの全国全件Crawlerを避け、需要のある求人から逆引きできるため
- JobDDの中心価値が求人件数ではなく応募経路Decision Supportだから
- Crawler/API開発が求職者Pain検証を食わないようにするため

2026-09-07時点でCareerjet APIは、JobDD用アカウントからHTTP 200で検索成功している。

検索条件 `機械設計 × 兵庫県 × 正社員` で、初期検証ドメインに適した実在求人を取得できることを確認した。

## HYPOTHESIS

## OPEN

# D-040｜Agentの非公開求人を前提に、公開求人件数とScoreを分離する

**日付：** 2026-09-07  
**Status：** 現在採用中／詳細設計は検証継続

## それまでの状態

JobDDでは、Agent比較のために、厚労省等の公的Fact、Agent公式サイトの公開情報、公開求人等を利用する方針を採用していた。

現行Score v0.1では「公開求人件数」も評価軸の1つとしている。

## 新しく得られた情報

人材紹介会社が保有する求人には、Web上に公開されない非公開求人が存在する。

そのため、

**Web上の公開求人件数は、Agentが実際に保有している総求人件数・求人保有力を完全には表さない。**

公開情報だけからAgentの保有求人全体を完全把握することはできない。

## 意思決定

1. Agentの公開求人件数を、総求人保有件数・求人保有力の代理指標として扱わない。
2. 公開求人は、対応職種・地域・年収帯・現在公開中求人との適合を確認するEvidenceとして利用する。
3. 公開情報が少ないこと自体を、求職者との低適合とみなさない。
4. 情報量・根拠の強さと適合Scoreを分離し、情報量の差は原則Evidence Level等で表現する。
5. 将来、Agentから非公開求人の属性情報等を提供してもらえる場合でも、提携・課金・データ提供量そのものをScoreへ直接加点しない。
6. 現行Score v0.1の「公開求人件数」は、正式Score設計時の見直し対象とする。

## 将来仮説

提携・同意・法的整理を前提として、企業名や求人本文を公開せず、

# D-043｜3経路のDiscovery母集団と代表候補への絞り込み構造を採用

**日付：** 2026-09-12  
**Status：** 現在採用中

## それまでの状態

Direct / Agent / Platformの3経路を比較し、各経路で具体候補TOP3程度を比較する基本構造は採用済みだった。

一方、全国・全業種へ拡張した場合に、膨大な企業・紹介事業者・Platformをどのように母集団化し、活動実態の異なる候補を公平に扱うかは未整理だった。

## 新しく得られた情報・議論

公的登録上は職業紹介事業者であっても、現在公開求人を出していない、紹介実績を確認できない、実質的な活動状況が不明な事業者が存在する一方、リクルートエージェントのような大規模事業者も存在する。

このため、登録母集団をそのまま全件Score化・ランキングすると、登録有無、活動量、会社規模、求職者との適合が混同される。

## 意思決定

JobDDは、Direct / Agent / Platformそれぞれについて、

**母集団 → Discovery → 活動・利用可能性確認 → Fit評価 → Evidence確認 → 今回比較する代表候補**

の段階構造を採用する。

第1階層では3経路を比較し、今回の条件で根拠が比較的強い経路を「今回の有力候補」として前面表示する。ただし他経路も確認可能とし、最終判断は求職者本人が行う。

第2階層では各経路内で代表3候補程度を比較する。

### Agent

公的な職業紹介事業者登録情報をRegistry母集団とし、以下を分離する。

- Registry
- Activity
- Fit
- Evidence

同一法人の複数事業所は法人・拠点関係を整理する。

公開求人件数の多さはFit Scoreへ直接反映しない。

### Direct

MVPではAgent / Platform等の実在求人から求人企業をDiscoveryし、企業公式採用ページを逆引きして直接応募可否を確認する。

### Platform

主要求人媒体・求人検索サービスのリストを母集団とし、API・公開検索・許可されたCrawler等で今回条件に近い求人Evidenceを確認する。

## 判断理由

- 大手・中小・専門特化型を会社規模や広告力だけで比較しないため
- 「登録されている」と「現在活動している」を分離するため
- 公開求人0件を不当に低評価しないため
- 巨大母集団から求職者が意思決定可能な候補数へ絞るため
- RecommendではなくDecision Supportの思想を維持するため

## OPEN

- Activityの正式判定ルール
- Evidence Levelとの関係
- Registryの全国母集団件数・単位の正確な確認
- 法人・支店・ブランドの統合ルール
- 代表3候補が最適か

# D-107｜求人Lifecycleへ `paused` を追加し、公開停止 / 再公開ルールを固定する

**日付：** 2026-10-02  
**Status：** 現在採用中

## それまでの状態

Phase Aでは求人の公開状態を `draft / published` を基本とし、`paused / closed` は将来拡張候補としていた。

企業側Controlled Publish実装後、実ブラウザE2Eで、

- 公開後の編集
- 差戻し
- 再申請
- Admin承認
- 再Publish

まで確認できた。

一方、採用充足・一時停止等により、公開済み求人を企業が即時に求職者向けから非表示にする運用が必要であることが確認された。

## 意思決定

求人Lifecycleへ `paused` を正式追加する。

`paused` は、

**一度承認・Publishされた求人を、企業の判断で求職者向け表示から一時的に外した状態**

とする。

公開停止は物理削除ではなく、求人データ・Published Snapshot・Job Fact・Evidence / Provenance・Application Route・過去の公開 / 審査情報は原則保持する。

求職者側では、`paused` 求人を一覧・詳細・比較・応募導線から非表示にする。

`closed` と公開済み求人の物理DELETEは今回の必須実装に含めない。

## 状態遷移

### 公開中から停止

```text
published + approved
↓ 公開を停止
paused + approved
```

### 停止中・内容変更なしの再開

```text
paused + approved
Authoring == Published Snapshot
↓ 公開を再開
published + approved
```

前回承認済みPublished Snapshotをそのまま再表示するため、再審査は不要とする。

### 停止中に編集した場合

```text
paused + approved
Authoring != Published Snapshot
↓
Preview
↓
再公開申請
↓
paused + pending_review
↓
Admin承認
↓
published + approved
```

未承認Authoringを直接公開しない。

### 再公開申請の差戻し

```text
paused + pending_review
↓ 差戻し
paused + changes_requested
```

企業は `review_note` を確認して修正し、再申請する。

### 更新審査中の緊急公開停止

```text
published + pending_review
↓ 公開を停止
paused + not_submitted
```

この場合、

- 現在公開中の求人を即時非表示
- Published Snapshotを保持
- 最新Authoringを保持
- 進行中の申請は取り下げ扱い
- `review_requested_at` 等の履歴情報は消去しない
- 再公開時はPreviewから改めて公開申請

とする。

## 企業Dashboard表示 / CTA

| 状態 | 公開状況 | 審査状況 | Primary CTA | Secondary |
|---|---|---|---|---|
| `published + approved` | 公開中 | 承認済み | 編集 | 公開ページを見る / 公開を停止 |
| `paused + approved`・差分なし | 公開停止中 | 承認済み | 公開を再開 | 編集 / Preview |
| `paused + approved`・差分あり | 公開停止中 | 更新作業中 | 編集を続ける | Preview |
| `paused + pending_review` | 公開停止中 | 再公開審査中 | 審査状況を見る | Preview |
| `paused + changes_requested` | 公開停止中 | 修正をお願いします | 修正する | 審査内容を見る / Preview |
| 再公開承認後 | 公開中 | 承認済み | 編集 | 公開ページを見る / 公開を停止 |

## 公開停止確認

企業が「公開を停止」を実行する際は、求職者向けから非表示になること、データと過去の公開内容は保持されることを明示する。

確認文言候補：

> この求人の公開を停止しますか？  
> 求職者向けの求人一覧・比較・応募導線から非表示になります。  
> 求人データと過去に承認された公開内容は保持されます。

## 削除方針

Phase A / v5.7では、公開済み求人の物理DELETEを通常運用にしない。

一度もPublishしていないDraftの削除は将来検討可能だが、一度Publishした求人は原則として公開停止、将来の募集終了等で扱い、履歴・Evidence・Provenanceを保持する。

## 判断理由

- 採用充足等で求人を即時非表示にできる必要がある
- Published Snapshot / Evidence / Provenanceの追跡性を維持するため
- 前回承認済み内容をそのまま戻す場合まで再審査すると企業負担が大きい
- 停止中に変更された未承認内容はControlled Publishを通す必要がある
- `closed`、物理削除、version管理等まで同時に広げずMVPスコープを維持するため

## 影響範囲

- `job_postings.status`
- Company Dashboard
- Dashboard CTA / Badge
- 求職者側公開フィルタ
- Preview
- Review Lifecycle
- Admin Review
- Application Route公開境界
- Feature Test / E2E

## OPEN

- `closed` の正式意味
- 掲載期限による自動停止
- Draft削除
- アーカイブUI
- 停止 / 再開履歴の専用監査ログ

# D-109｜Demo専用システム分岐を追加せず、入力内容と安全な非応募URLで卒業制作Demoを運用する

**日付：** 2026-10-03  
**Status：** 現在採用中

## それまでの状態

D-108では、卒業制作審査期間中に限り、Demoであることを明示した架空Company / Demo求人を本番公開可能とした。

その後のProduction Preflight監査で、現行実装では、

- Publish Validatorが応募URLを必須としている
- 承認時に応募URLからApplication Routeを生成する
- 通常の公開フローにDemo専用CTA無効化処理は存在しない

ことが確認された。

そのため、

「Demo求人だけ応募URLを不要にする」
「Demo専用 `is_demo` フラグを追加する」
「Demo専用Publish分岐を追加する」

等の実装案を検討した。

## 得られた情報

卒業制作審査では、Demo専用システムを見せたいのではなく、

**通常のJobDD企業アカウント / Dashboard / Controlled Publish / Decision View / pausedが、本番同様に動くこと**

を確認してもらうことが目的である。

また、卒業制作提出直前にDemo専用migration・状態・UI分岐を追加すると、

- 通常求人ロジックへの影響
- テスト範囲増加
- 本番deployリスク
- 卒業制作後に不要な特殊仕様が残る

可能性がある。

## 意思決定

卒業制作Demoのために、

- `companies.is_demo`
- `job_postings.is_demo`
- Demo専用Account Type
- Demo専用Publish Validator
- Demo専用Application Route
- Demo専用CTA分岐

等は追加しない。

卒業制作審査では、通常の企業アカウントとして、

```text
JobDDテスト株式会社
```

を利用する。

Demoであることは、システム状態ではなく**入力内容によって明示**する。

求人タイトル例：

```text
【卒業制作デモ・応募不可】産業機械の機械設計エンジニア
```

求人詳細冒頭例：

> この求人はJobDD卒業制作の動作確認用デモです。実際の募集ではありません。応募はできません。

## 応募URL / Application Route

通常のPublish Validator / Controlled Publishを変更しない。

応募URL必須仕様を維持し、Demo求人には、

**JobDD内の安全な非応募URL**

を設定する。

例：

```text
https://jobdd.jp/
```

Application Route / CTAが生成される場合も、このURLは実応募先ではない。

実在企業、求人媒体、人材紹介会社等の応募先へ接続しない。

したがって、卒業制作Demoは、

**データはDemo、システム挙動は通常**

という原則で運用する。

## Dashboard / 審査体験

審査員は `JobDDテスト株式会社` で通常の企業ログインを行い、

- Company Dashboard
- 求人状態
- Level 1 / Level 2
- Preview
- 公開申請
- 審査状況
- Account Settings
- paused / 再開

等を通常企業と同じUI / Lifecycleで確認できる。

Demo専用DashboardやDemo専用権限は作らない。

## D-108との関係

D-108の、

- Demoであることを明示する
- 実応募へ接続しない
- 審査終了後 `paused` とする
- 通常運用で架空求人を恒常公開しない

という原則は維持する。

一方、

**Demo応募導線の実現方法**

についてはD-109を最新Decisionとする。

応募URLを空にすることやDemo専用CTA制御を必須とはせず、既存Publish仕様に従って安全なJobDD内URLを利用する。

## 判断理由

- 卒業制作専用コードを本番へ増やさないため
- 通常のControlled Publishをそのまま審査してもらうため
- Publish Validator / Application Routeの通常仕様を壊さないため
- migrationを追加しないため
- 提出直前の回帰リスクを最小化するため
- Demo運用終了後に不要な特殊機能を残さないため

## 影響範囲

コード変更は原則不要。

主に以下のDemo入力データ / 運用へ影響する。

- Company名
- 求人タイトル
- 求人本文
- application_url
- Production Smoke手順
- 卒業制作審査後のpaused運用

## HYPOTHESIS

なし。

本Decisionは事業仮説ではなく、卒業制作審査の運用方針である。

## OPEN

- Demo求人の具体的な公開終了日時
- `paused` 実行担当 / タイミング
- `noindex` の採否
- 将来のDemo案内専用ページ
- 将来の実在Company / 実在求人を用いた正式Production Smoke
