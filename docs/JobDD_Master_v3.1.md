# 1. 情報の分類ルール

JobDDでは、以下を明確に区別する。

## FACT｜確認済み事実

インタビュー、公開情報、実際の行動、計測結果などから確認できたもの。

## DECISION｜意思決定

検証結果などをもとに、現在採用している方針。

## HYPOTHESIS｜仮説

## OPEN｜未検証・未決定

今後検証または意思決定が必要なもの。

JobDDについて議論する際、FACTとHYPOTHESISを混同しない。

# 2. JobDDとは

## DECISION｜卒業制作モックは統合版1本で進める

JobDD / JobDDDを別サービスとして分けず、

**Direct（企業への直接応募）／Agent（人材紹介会社）／Platform（求人媒体等）を横断し、求職者が自分に合う応募経路を比較して選べるDecision Supportサービス**

として、統合版モック1本で検証する。

JobDDは、AIが応募経路を決定するサービスではない。

AIは、

- 情報収集
- 応募経路の整理
- 比較
- 各経路のメリット・デメリット整理
- 適合理由の説明
- 根拠の提示

を担当する。

最終判断は求職者本人が行う。

## HYPOTHESIS｜新しい価値仮説

求職者は、

**「どの求人に応募するか」だけでなく、「その求人へどの経路で応募するのが自分にとって最も良いか分からない」**

という課題を持っている可能性がある。

応募経路には、少なくとも以下がある。

- Direct：企業公式採用ページ等から直接応募
- Agent：人材紹介会社経由
- Platform：求人媒体・転職プラットフォーム経由

従来は「直接応募が最も強い／得」と考えがちだったが、実際には求人ごとに正式ルートや得られる支援・利便性が異なる。

そのためJobDDは、

**「必ずDirectへ誘導するサービス」ではなく、「求職者ごと・求人ごとに各応募経路を比較できる状態を作るサービス」**

を目指す。

## DECISION｜Direct / Agent / Platformすべてで具体候補TOP3を比較できる構造を採用する

第1階層では、

**Direct / Agent / Platform の3経路そのものを比較する。**

そのうえで第2階層では、Agentだけでなく、3経路すべてについて具体候補を比較できる構造とする。

1. 第1階層：Direct / Agent / Platform の経路比較
2. 第2階層：各経路内の具体候補TOP3比較

具体的には、

- Direct：直接応募可能な企業・求人候補TOP3
- Agent：人材紹介会社候補TOP3
- Platform：求人媒体・転職Platform候補TOP3

を基本構造とする。

ただし、**TOP3という候補数自体が最適か、3経路すべてで複数候補比較が求職者の意思決定に本当に必要かはHYPOTHESIS**であり、ユーザー検証で確認する。

JobDDはTOP3を「おすすめ決定」として提示するのではなく、候補を絞って比較しやすくするDecision Supportとして扱う。

## 基本思想

JobDDの基本思想は従来どおり、

**RecommendではなくDecision Support**

とする。

# 3. JobDDが解決しようとしている課題

## 求職者側の課題

### HYPOTHESIS｜従来仮説

転職を考えている求職者は、

**「自分に合う人材紹介会社がどこなのか分からない」**

という課題を抱えている可能性がある。

この仮説はまだ未検証であり、FACTではない。

### HYPOTHESIS｜統合版で追加された上位仮説

求職者は、

**「自分に合う応募経路が分からない」**

という課題を持っている可能性がある。

たとえば同じ求人でも、

- 企業公式から直接応募する
- 人材紹介会社を経由する
- ビズリーチ等のPlatformから応募する

という複数の選択肢が存在し得る。

また、必ずしもDirectが常に最適とは限らない。

JobDDは、各経路の

- 正式性
- 応募可否
- メリット
- デメリット
- 手間
- 支援内容
- 情報量
- 求職者との適合性
- 根拠の強さ

を整理し、求職者自身が選べる状態を作る。

### FACT｜東京科学大学の公開求人で得た観察

2026-08-27に公開情報を確認した東京科学大学の一部募集では、

**ビズリーチ上での応募に加え、大学指定の提出手続きが必要な募集が確認された。**

このケースから、

**「企業へ直接応募できること」と「その求人にとって正式・適切な応募経路であること」は同義ではない**

ことが確認できた。

ただし、この1事例だけで求職者全体のPainを証明するものではない。

# 4. 初期スコープ

## DECISION｜最初の検証対象は「機械設計・機電系」を中心に尖らせる

2026-09-02の第1回メンタリングを踏まえ、卒業制作MVPの初期検証では、

**機械設計・機電系を中心とする製造・プラント系技術職**

を最優先の検証ドメインとする。

これは全国・全職種への将来拡張を否定するものではない。

ただし、初期段階では、

- 池田徹自身の30年以上の機械設計ドメイン知識を使える
- 採用側で機械設計・機電系人材の獲得難が確認・示唆されている
- 初期集客時に「誰向けのサービスか」を明確にできる
- 求職者インタビュー対象を具体化できる
- Score・Evidenceの妥当性を人間側でもレビューしやすい

という理由から、広げるより先に尖らせて検証する。

## FACT｜現在の入力UIは広い条件を入力できる

2026-09-02時点のデプロイ済みモックでは、

- 希望職種
- 希望業界
- 希望勤務地（都道府県・市区町村）
- 希望年収
- 経験年数
- その他の希望・相談内容

を入力できる。

UI上は他職種も入力可能だが、**それは全国・全職種で十分なデータ品質を保証することを意味しない。**

## OPEN｜全国・全職種へ広げるタイミング

全国・全職種化は将来候補として維持する。

ただし、最初に確認すべきなのは、

> 機械設計・機電系の求職者が、応募経路や人材紹介会社を比較して選ぶことに本当に価値を感じるか。

である。

この仮説が支持された場合、職種・地域を段階的に拡張する。

# 6. JobDD Score

## FACT｜現在実装中のScore v0.3

2026-09-08時点の検証用MVPでは、人材紹介会社との適合Scoreを以下4軸で算定している。

1. 職種適合
2. 地域適合
3. 経験年数適合
4. 年収適合

Score計算には、`agency_facts` のうち **verification_status = verified** のFactのみを利用する。

確認済みFactが存在しない軸は0点として扱わず、**未確認（null）** とする。
最終Scoreは、確認済みの軸だけを対象に単純平均して算出する。

また、画面上ではScoreと併せて、

**「確認済み ○ / 4軸」**

を表示し、Scoreの高さとEvidence量を分離して確認できるようにしている。

### DECISION｜公開求人件数をScoreから除外

Agentには非公開求人が存在するため、Web上の公開求人件数は総求人保有力を完全には表さない。

そのためScore v0.3では、従来の `public_job_count` をScore計算から除外した。

`public_job_count` 自体はEvidenceとして保持できるが、件数が多いことをそのままAgent適合度の高さとして加点しない。

### FACT｜職種・地域の判定を実在データ向けに補正

Score v0.3では、完全一致だけでなく、以下のような包含関係も扱えるようにしている。

- 希望職種がFact内に含まれる場合
- Factが「全職種」の場合
- 希望地域がFact内に含まれる場合
- Factが「全国」「日本国内」等の場合

これは実在Agentの公開Factを使った比較で、過度な完全一致判定を避けるための最小修正である。

## OPEN｜正式なScore設計

Score v0.3は検証用の暫定実装であり、正式仕様ではない。

今後、

- 4軸を維持するか
- 業界適合を追加するか
- 詳細スキル適合をScoreへ含めるか
- 重み付けを行うか
- 未確認軸が多い場合の表示方法
- 100点満点を維持するか
- Scoreより理由・Evidenceを前面に出すか

を求職者検証と実データ品質を踏まえて決める。

JobDD ScoreはAIによるブラックボックス評価ではなく、引き続き

**説明可能なルールベース＋根拠表示**

を基本思想とする。

## DECISION｜詳細スキル入力は任意・選択式を基本とする

機械設計・機電系の求職者について、職種名だけでは実際の専門性を十分に表現できない場合がある。

そのためMVPでは、希望条件入力に **詳細スキル（任意）** を追加する方向で進める。

入力負荷を抑えるため、自由記述を必須とせず、プルダウン・複数選択・タグ選択等の **候補から選ぶ方式** を基本とする。

初期候補の例：

### 使用ソフト / Tool

- AutoCAD
- Inventor
- SolidWorks
- CATIA
- Creo
- NX

### 専門スキル / Skill

- 強度計算
- FEM
- 製図
- GD&T
- 3Dモデリング
- 配管設計
- 機構設計

### 経験分野 / Domain

- 発電プラント
- 産業機械
- 自動車
- 半導体製造装置
- 設備

選択肢にない場合は「その他」等の自由入力を補助的に用意することを検討する。

## HYPOTHESIS｜詳細スキルと実在求人の一致をAgent比較Evidenceに使う

詳細スキルは、現時点ではJobDD Scoreへ直接加点することを主目的としない。

まずは、各Agentの公開求人や確認済み求人Evidenceに対して、

> **「あなたが選択した詳細スキルと一致する求人を、このAgentで確認できたか」**

を表示するために利用する。

例えば、

- AutoCAD
- Inventor
- 強度計算
- 配管設計
- 発電プラント

等のユーザースキルと、Agentが公開している実在求人の要件・仕事内容が一致しているかを根拠URL付きで整理する。

これにより、単なる「機械設計を扱っている」という会社属性より、求職者本人に近い具体的なEvidenceを提示できる可能性がある。

## OPEN｜詳細スキル設計

- MVPで用意する選択肢の正式リスト
- Tool / Skill / Domainの分類粒度
- 何件まで選択できるようにするか
- 求職者が入力負荷を感じないか
- 求人本文から詳細スキルをどの程度安定抽出できるか
- 表記揺れ・同義語をどう正規化するか
- 詳細スキル一致を将来正式Score軸へ含めるか
- 職種ごとのDomain Packへ発展させる必要があるか

### MVP上の注意

詳細スキル入力は **任意** とし、入力しなくてもJobDDを利用できる状態を維持する。

また、卒業制作ではスキル辞書の網羅性を目的化しない。
最優先は、詳細スキルEvidenceが求職者のAgent比較・応募経路比較の納得感を本当に高めるかを検証することである。

# 9. MVP

## DECISION｜統合版モックを1本で制作する

卒業制作の初期モックは、JobDD / JobDDDを分けず、

**Direct / Agent / Platform を1つの画面体験の中で比較できる統合版JobDD**

として制作する。

### MVPで検証したい中心仮説

> 求職者は、求人・企業公式・人材紹介会社・求人媒体など複数の選択肢があるとき、
> 自分に合う応募経路を比較し、根拠を確認したうえで納得して選びたいというPainを持っているか。

検証結果は職種・業界・地域タグ別にも確認し、特に製造・プラント系ではドメイン知識を活かして深く検証する。

### 必須候補

1. 求職者プロフィール・希望条件入力
2. 求人または転職希望条件の入力
3. Direct / Agent / Platform の応募経路整理
4. 各経路のメリット・デメリット・適合理由表示
5. 根拠情報 / Evidence Level表示
6. Direct / Agent / Platformそれぞれの具体候補TOP3比較
7. 最終判断を求職者本人に委ねる導線

### モックの基本画面構成案

1. 条件入力
2. 応募経路サマリー
3. Direct / Agent / Platform 比較
4. 経路詳細
5. Direct / Agent / Platform各経路のTOP3候補比較
6. 次の行動選択

実装可否より、

**この体験そのものに求職者が価値を感じるか**

を優先して検証する。

# 11. ビジネスモデル

## HYPOTHESIS｜現時点のマネタイズドラフト

岩下さんからは、卒業制作段階ではマネタイズを優先しすぎない方針が示されている。

その前提で、現時点では以下をドラフトとして持つ。

### 求職者側

- 初回相談：無料
- 初回無料の代わりにLINE登録を得る
- 良い求人・応募経路が見つかった場合、LINEで通知する
- 2回目以降の相談：1回500円

### 企業側

- 初回の接点提供：無料
- 継続的にJobDD経由の求職者接点を受けたい企業には有料契約を検討
- 料金ドラフト：1件1万円

ただし、以下はまだ確定していない。

## DECISION｜課金有無で比較結果を変えない

企業・人材紹介会社・Platformから収益を得る場合でも、

**課金有無を応募経路の比較結果・JobDD Score・表示順位へ反映しない。**

未契約企業であっても、その企業の公式応募ルートが求職者にとって有力であれば、比較候補として表示できる設計を維持する。

JobDDが課金する対象は、

**「比較結果に載せること」ではなく、追加の接続機能・高適合な接点・継続的な送客価値等**

と分離して考える。

## OPEN｜法的整理

企業へ特定求職者を有料でつなぐ設計は、実装・運用方法によって職業紹介に該当する可能性がある。

そのため、

- どの行為が職業紹介に該当するか
- 許可不要で成立するDecision Support / 情報提供の範囲
- B2B課金をどの商流で成立させるか

は法的確認が必要。

卒業制作段階では、課金機能の完成よりも、

**求職者がこのDecision Supportに価値を感じるか**

の検証を優先する。

# 12. 未提携紹介会社も掲載する構想

## HYPOTHESIS

JobDDでは、提携済み紹介会社だけを検索対象にすると、

「本当に求職者に合う会社」

ではなく、

「JobDDと契約している会社」

だけを紹介するサービスになってしまう。

そのため、

**未提携会社も比較対象として掲載する**

構想を持つ。

求職者が未提携会社を選択した場合、

その選択を需要データとして蓄積する。

例：

「○○社を選びたい」

という需要が多ければ、

JobDD側からその紹介会社へ

「すでに○人の求職者が御社への相談を希望しています」

という営業ができる。

つまり、

**需要を先に作り、需要のある紹介会社から提携する。**

# 13. JobDDの差別化仮説

### HYPOTHESIS

一般的な転職サービスは、それぞれ自社の経路へユーザーを導く構造を持つ。

例：

- 求人媒体：自社媒体内で応募
- 人材紹介会社：自社経由で応募
- 企業採用ページ：企業へ直接応募

JobDDは、その一段上で、

**Direct / Agent / Platform を横断して比較するメタレイヤー**

に位置する。

JobDD自身が特定の経路へ恣意的に誘導するのではなく、

**求職者にとって各経路がどう違うかを整理し、本人の意思決定を支援する。**

### HYPOTHESIS｜将来像

JobDDは単なる「求人検索」や「人材紹介会社比較」ではなく、

# 31A. 課金者と利用者の価値整合

## DECISION

JobDDでは、

**求職者への価値提供と、人材紹介会社への課金価値を、同じ成果の表裏として設計する。**

求職者に対しては、

- 自分に合う人材紹介会社を登録前に比較できる
- なぜ自分に合うのかを理解できる
- 自分で相談先を選べる

という意思決定支援を提供する。

その結果として人材紹介会社には、

**自社の得意領域と適合し、かつ本人が相談意思を持った求職者との接点**

を提供する。

つまり、

> **求職者にとってのBetter Choiceが、人材紹介会社にとってのBetter Leadになる。**

という構造を基本とする。

---

## 31A-1. 人材紹介会社への提供価値

### FACT

人材紹介会社へのインタビューでは、

- 求職者が集まらない
- 集まった求職者と自社求人とのマッチ度が低い

というPainが確認されている。

### HYPOTHESIS

JobDD経由で、

- 自社の得意領域と適合している
- 求職者本人が比較・納得したうえで相談を希望している

という状態の求職者を送客できれば、通常の広告リード等より高い価値を感じてもらえる可能性がある。

人材紹介会社がJobDDに支払う理由は、単なる「掲載」ではなく、

**高適合かつ相談意思のある求職者との接点**

とする。

---

## 31A-2. ランキングと課金を分離する

## DECISION

JobDD Score、TOP3比較、適合理由等の表示順位は、

**人材紹介会社の課金有無によって変更しない。**

課金企業を優先表示することは、JobDDが目指す

**RecommendではなくDecision Support**

という思想と矛盾するため、原則として行わない。

基本構造は、

1. 求職者との適合性をもとに比較候補を提示する
2. 求職者が自分で相談先を選ぶ
3. 求職者が相談を希望した結果として、人材紹介会社側に価値が発生する
4. その価値に対して人材紹介会社へ課金する

とする。

つまり、

> **「お金を払った会社を表示する」のではなく、「求職者に選ばれた結果として課金価値が生まれる」**

構造を目指す。

---

## 31A-3. 利益相反を防ぐ設計原則

JobDDでは、人材紹介会社から課金することにより、サービスが課金者都合へ最適化されるリスクを認識する。

そのため、以下を設計原則とする。

- 課金有無をJobDD Scoreへ反映しない
- 課金有無をTOP3等の比較順位へ反映しない
- 未提携会社も比較対象に含める構想を維持する
- AIが登録先を決定せず、最終判断は求職者本人が行う
- 広告・スポンサー表示等を将来導入する場合は、客観的な比較結果と明確に分離する

JobDDは、

**人材紹介会社の営業都合で求職者を誘導するサービスではなく、求職者の意思決定の質を高めることで、結果的に紹介会社にも高品質な接点を提供するサービス**

とする。

---

## 31A-4. 現時点で未検証の事項

### OPEN

以下はまだ確認できていない。

- JobDD経由の求職者が、実際に通常リードより高マッチになるか
- 人材紹介会社が「高適合＋相談意思あり」の求職者に支払意思を持つか
- どの段階で課金するのが最も合理的か
- 相談申込1件あたり等、具体的にいくら支払うか
- 求職者側の登録前比較Painが十分に強いか

したがって、卒業制作段階では、課金モデルの精緻化よりも、

**求職者が本当にJobDDを使い、自分で比較して相談先を選ぶか**

の検証を優先する。



# 31B. 公平な比較市場としてのJobDD

## VISION

JobDDは、

**自社集客基盤や巨大なプラットフォームを持たない人材紹介会社でも、専門性と求職者との適合性によって選ばれる機会を持てる市場**

を目指す。

求職者にとっては、

**「有名だから選ぶ」から「自分に合っているから選ぶ」へ**

人材紹介会社にとっては、

**「広告費や知名度で競う」だけでなく「得意領域と適合性で選ばれる」へ**

という選択構造を作る。

ただし、JobDDは中小人材紹介会社を恣意的に優遇するサービスにはしない。

## DECISION

JobDDでは、

- 大手だから加点しない
- 中小だから加点しない
- 会社規模そのものを有利・不利の評価軸にしない
- 知名度そのものをJobDD Scoreの評価軸にしない
- JobDDへの課金有無をScoreや比較順位へ反映しない

という原則を採用する。

比較の中心は、

**「この求職者に、この人材紹介会社がどれだけ適合しているか」**

とする。

その結果として、知名度が低くても特定職種・業界・地域・経験層などに強い人材紹介会社が、大手より高い適合度を示すことを許容する。

逆に、大手人材紹介会社の方が求職者に適している場合は、大手が高く評価される。

JobDDが作る公平性とは、

**中小を勝たせることではなく、同じ評価基準で適合性を比較できる状態を作ること**

と定義する。

## HYPOTHESIS

特に、

**独自の大規模な求職者集客基盤を持たない、専門特化型・中小人材紹介会社**

は、JobDDによって自社の得意領域に適合した求職者から発見されることに高い価値を感じる可能性がある。

ただし、この支払意思・利用価値は未検証である。

## OPEN

- どの範囲の人材紹介会社をMVPの比較対象に含めるか
- 大手総合型人材紹介会社と専門特化型人材紹介会社を同一画面で比較する場合の表示方法
- 求職者が会社規模や知名度より適合理由を重視するか
- 中小・専門特化型人材紹介会社がJobDD経由の高適合リードに支払意思を持つか

---

# 31C. JobDD Scoreのデータ・採点原則

## DECISION

JobDD Scoreは、

**公的・客観的・検証可能な情報を採点の基礎とする。**

MVPでは、主に以下の情報源を想定する。

### 1. 公的・構造化データ

例：

- 厚生労働省「人材サービス総合サイト」等の公開情報
- 職業紹介事業の許可情報
- 取扱職種
- 取扱地域
- 就職者数等の公開実績
- その他、第三者が確認可能な公的情報

これらはJobDD Scoreの基礎データとして優先的に利用する。

### 2. 人材紹介会社の公式サイト

企業公式サイトも情報源として利用する。

ただし、Scoreへ直接反映するのは、原則として

**第三者が同じページを見て確認できる、検証可能な事実**

とする。

例：

- 公開求人件数
- 対応職種
- 対応業界
- 対応地域
- 拠点
- 公開求人の勤務地
- 公開求人の年収帯
- 対象経験層等の明示情報

### 3. 自己申告的・定性的表現

以下のような表現は、原則としてその文言だけでは直接加点しない。

例：

- 「製造業に強い」
- 「業界トップクラス」
- 「手厚いサポート」
- 「高い専門性」
- 「豊富な求人」

これらは比較画面上の参考情報として表示することはできるが、

**マーケティング表現の巧拙がScoreに影響しない設計**

を優先する。

可能な場合は、その主張を公開求人・実績・取扱職種等の検証可能な情報へ変換して評価する。

---

## DECISION｜会社属性ではなく求職者との適合を採点する

JobDD Scoreは、

**「良い人材紹介会社ランキング」ではない。**

測定対象は、

> この求職者と、この人材紹介会社の適合度

とする。

そのため、以下は原則としてScoreへ直接反映しない。

- 会社規模
- 売上高そのもの
- ブランド知名度
- 広告出稿額
- JobDDへの課金額
- JobDDとの提携有無

---

## HYPOTHESIS｜主要評価軸候補

MVPのJobDD Scoreでは、以下を主要評価軸候補とする。

- 職種適合
- 業界適合
- 地域適合
- 経験レベル適合
- 年収レンジ適合
- 現在の公開求人との適合
- その他、求職者インタビューで重要性が確認された項目

具体的な配点はまだ確定しない。

求職者インタビューおよび実データによる採点シミュレーションを通じて検証する。

---

## HYPOTHESIS｜Evidence Level

JobDD Scoreとは別に、

**そのScoreをどの程度強い根拠で算定できているかを示すEvidence Level**

を設けることを検討する。

考え方の例：

- 公的情報・公開求人・実績等から十分に確認できる
- 公式サイト情報を中心に確認できる
- 情報不足により推定要素が多い

Scoreと根拠の強さを分離することで、求職者自身が情報の確からしさも含めて判断できる状態を目指す。

これはJobDDの

**RecommendではなくDecision Support**

という思想に沿う。

---


## HYPOTHESIS｜類似求職者の紹介・応募・成約実績を将来の適合Evidence / Score候補とする

JobDDでは、単純な会社全体の紹介実績件数ではなく、

**「この求職者に近い条件の人が、その人材紹介会社でどのような結果になったか」**

を、将来の比較Evidenceとして活用できる可能性がある。

想定する類似条件の例：

- 職種
- 地域
- 年収帯
- 経験年数
- 業界
- その他、求職者インタビューで重要性が確認された属性

将来取得候補となる実績：

- 類似求職者の相談実績件数
- 類似求職者の紹介実績件数
- 類似求職者の応募実績件数
- 類似求職者の内定実績件数
- 類似求職者の入社・成約実績件数

単純な件数の多さだけで評価すると、事業規模の大きいAgentが有利になる可能性がある。
そのため、将来的に利用する場合も、

**「総件数の多さ」ではなく「類似条件における適合実績」**

として扱う。

また、紹介件数だけでなく、

**相談 → 紹介 → 応募 → 内定 → 入社**

のどこまで進んだかを確認できれば、より強いEvidenceになる可能性がある。

### HYPOTHESIS

類似求職者の実績データを蓄積できれば、公開情報だけでは分からないAgentとの実適合を比較でき、JobDDの独自データ資産になり得る。

これは、JobDDが目指す

**「使われるほど強くなるDecision Support」**

とも整合する。

### OPEN

- 人材紹介会社が匿名集計された実績データを提供するか
- 紹介件数・応募件数・成約件数のどこまで取得可能か
- 類似条件の定義
- 母数が少ない場合の表示・Score処理
- 大手Agentの母数優位をどう補正するか
- 実績件数と実績率のどちらを重視するか
- JobDD自身の利用データをどの時点から利用するか
- 同意・プライバシー・法的整理
- Evidenceとして表示するだけにするか、正式Score軸へ含めるか

### MVP上の扱い

卒業制作MVPでは、この実績データ取得基盤を先に作らない。

現段階では、

**将来のEvidence / Score候補となるHYPOTHESIS**

として保持する。

まずは公開・確認可能なFactを使った比較と、求職者本人へのPain / Decision Support価値検証を優先する。

求職者インタビューでは、

> 「自分と近い職種・地域・年収帯の人が、その紹介会社経由で応募・転職した実績」

が比較材料として価値を持つかも確認候補とする。

---
## OPEN｜今後の検証事項

- 各評価軸の配点
- 各情報源から安定的に取得できる項目
- 公式サイト情報をどこまで自動抽出できるか
- 求人件数を単純な多さで評価すべきか
- 就職者数など事業規模に比例しやすい指標をどう正規化するか
- 求職者が実際に重視する比較項目
- Scoreそのものと適合理由説明のどちらを重視するか
- Evidence Levelが意思決定に役立つか

卒業制作MVPでは、アルゴリズムの完成度よりも、

**客観的な比較情報と適合理由が、求職者の人材紹介会社選びに実際に役立つか**

の検証を優先する。

# 31D. AI時代の模倣耐性と、JobDDに積み上げる資産

## 背景

2026-08-28、那珂慎二氏のコラム
「そのアプリ、なぜあなたが作る必要があるのか
――AI時代に『模倣されないサービス』をつくるための思考法」
を受け、JobDDの設計原則を整理した。

コラムの中心的な示唆は、

- 「AIを使っていること」自体は差別化になりにくい
- 実装可能性より、「何を作るべきか分かっていること」の価値が高い
- AIへ判断を丸投げすると、独自の専門性や判断軸が薄れる
- 模倣されない秘密技術を守るより、模倣されても勝てる資産を積み上げる
- 独自データ、体験設計、業界知識、人間の信頼・関係性を時間とともに蓄積する

という考え方である。

JobDDではこの考えを、AI導入そのものを目的化しないための設計原則として採用する。

---

## DECISION｜AIはJobDDの主役ではなく手段とする

JobDDの差別化を、

**「AIを使っていること」そのものには置かない。**

AIは主に、

- 公開情報の収集・整理
- 比較材料の構造化
- 適合理由の文章化
- 根拠情報の提示
- ユーザーが判断しやすい形への要約

に利用する。

一方で、JobDDの中核となる

- 何を評価するか
- どの情報を重視するか
- どの条件で評価を変えるか
- どの情報を根拠として信頼するか
- 最終的に何をユーザーへ見せるか

という判断設計は、JobDD側が明示的に設計する。

これは既存の

**RecommendではなくDecision Support**

という思想とも一致する。

---

## DECISION｜JobDD Scoreの判断軸を独自資産として育てる

JobDD Scoreを、汎用AIへ

「この人に合う会社を採点して」

と丸投げする方式にはしない。

MVPでは引き続き、

**説明可能なルールベース＋根拠表示**

を優先する。

特に、

- 評価軸
- 判定ルール
- 重み付け
- N/Aの扱い
- Evidence Level
- 求職者属性による評価変化

を、検証結果をもとにJobDD独自の判断ロジックとして育てる。

ただし、現時点の評価軸・配点は完成済みのFACTではない。

### HYPOTHESIS

現在検討しているスコアリング設計が、実際の求職者の意思決定に役立つ可能性がある。

求職者インタビュー、モック検証、実データによるバックテストを通じて、軸・重み・表示方法を継続的に修正する。

---

## HYPOTHESIS｜JobDDは「使われるほど強くなる」構造を持てる

将来的に、適切な同意・プライバシー保護・法的整理を前提として、JobDD利用から以下のデータが蓄積される可能性がある。

- どの属性の求職者が
- どの求人・企業を検討し
- Direct / Agent / Platform のどの経路を比較し
- どの経路を選び
- Agentを選んだ場合にどの紹介会社を選び
- どの比較理由を重視し
- その後どのような結果・満足度になったか

これらが蓄積されれば、JobDDは単なる公開情報比較から、

**実際の求職者行動・意思決定・結果を反映できるDecision Support**

へ進化できる可能性がある。

これは後発が画面やコードを模倣しても、短期間では再現しにくい

**時間差の資産**

になり得る。

ただし、これは現時点では将来仮説であり、卒業制作MVPで大量データ収集を目的化しない。

---

## DECISION｜積み上げるべき4つの資産を意識する

JobDDでは、模倣耐性を高める資産として以下を意識する。

### 1. 独自データ

将来的な候補：

- 求職者の比較行動
- 応募経路の選択
- 紹介会社選択
- 適合理由への反応
- 相談・応募・転職結果
- 求職者評価

ただし、MVPでは必要最小限とし、Pain検証を優先する。

### 2. 体験設計

単なるチャットUIではなく、

- 比較しやすい
- 根拠を確認しやすい
- 選択肢の違いを理解しやすい
- 最終判断を自分で行いやすい

というDecision Support体験を、モックとユーザー観察から磨く。

### 3. 現場で得る業界知識

- 製造・プラント系技術職のキャリア理解
- 人材紹介会社の得意不得意
- 採用企業側の事情
- 応募経路ごとの実務上の違い
- 現場で使われる判断基準

を、インタビューと実際の調査から蓄積する。

Google検索や汎用AIだけで得られる知識に依存しない。

### 4. 人間の信頼・関係性

- 求職者
- 人材紹介会社
- キャリアコンサルタント
- 採用企業
- 業界経験者
- 将来の専門家・監修者

との関係を、コードとは別の事業資産として育てる。

---

## DECISION｜模倣耐性より先にPain検証を置く

重要な注意として、

**「模倣されないサービスを作ること」自体を卒業制作の目的にはしない。**

現時点の最重要OPEN QUESTIONは、

> 求職者は、Direct / Agent / Platform等の応募経路を比較し、
> 根拠を確認しながら自分で納得して選びたいというPainを本当に持っているのか？

である。

製造・プラント系技術職は、この上位仮説を深く検証する重要な検証ドメインとして扱う。

Painが確認できていない段階で、

- 大規模データ基盤
- 高度なAI
- 複雑な学習機構
- ロックイン設計
- 大規模コミュニティ

を先に作らない。

まず、

**Painがある → JobDDのDecision Supportが使われる → 使われる過程で資産が積み上がる**

という順番を守る。

4. **ユーザーが使うたびに何が資産として残るか**

# 35. DB / MVPスコープ更新（2026-08-29）

> **2026-09-02更新:** 本節の「表向き全国・全業種」方針は、初期検証を機械設計・機電系へ尖らせる最新DECISIONにより一部上書きされた。技術的な拡張性・タグ設計は維持する。

## 過去DECISION｜表向きの地域・業種制限を外す

卒業制作モックでは、ユーザー向けUI上で地域・業種・職種の利用制限を設けない。

ユーザーは全国・全業種の条件を入力できる設計とする。

ただし、内部では以下のタグを保持し、後から分析・検証・必要に応じた制限ができる構造とする。

- region_tag
- industry_tag
- occupation_tag
- validation_domain
- score_model_version

この変更は、従来の「製造・プラント系技術職に限定して利用させる」スコープから、

**表向きは全国・全業種、内部では検証単位を保持する**

設計への変更である。

なお、求職者インタビューや分析では、職種・業界ごとの差を混ぜずに確認する。

---

## DECISION｜人材紹介会社DBは厚労省登録情報を母集団とし、事前収集＋オンデマンド補完で育てる

人材紹介会社については、厚生労働省等の公的な登録情報を母集団として保持する。

加えて、**取得条件・利用条件・更新コストの面で問題がない公開情報については、ユーザー要求が発生する前に可能な範囲で事前収集し、DBへストックする。**

一方で、全国・全業種について最初から完全な詳細データを揃えることは目的にしない。

ユーザー要求が発生した際は、まず既存DBを優先参照し、

- 情報が不足している
- 情報が古い
- 当該求人・当該経路だけ追加確認が必要
- 構造化されていない公開情報から事実抽出が必要

といった部分だけをオンデマンドで追加調査する。

基本フローは以下とする。

1. 公的データ・利用可能な公開情報から、取得可能な基本データを事前収集
2. ユーザーの自然文コメントや求人URLを取得
3. AIで職種・業界・地域・年収・経験等へ構造化
4. 既存DBからDirect / Agent / Platform候補と保存済みfactsを取得
5. 情報の欠損・鮮度・Evidenceを確認
6. 不足・期限切れ部分だけAI/API等で追加調査
7. 調査結果を根拠URL・取得日時等を伴う検証可能な事実としてDBへ保存
8. JobDD独自ルールでScoreを算出
9. 比較結果とEvidenceを表示
10. 今回取得した事実を次回以降も再利用する

この方式を、

**事前収集DB＋差分更新＋オンデマンドAI/API補完**

のハイブリッド方式とする。

従来の「厚労省母集団＋需要起点のオンデマンド追加調査」は撤回せず、**事前収集可能な情報を先に蓄積する方向へ拡張したもの**として扱う。

---

## DECISION｜AIは「判断値」ではなく「根拠付き事実」を収集する

AI調査では、

「この会社は製造業に強い＝85点」

のような評価値をそのまま保存しない。

保存するのは、第三者が再確認できる事実と根拠である。

例：

- 機械設計求人18件
- 兵庫県求人7件
- 年収600万円以上求人11件
- 公式サイトで確認した対応地域
- 厚労省登録情報
- 情報源URL
- 取得日時

Scoreはこれらの事実からJobDD側の明示的なルールで計算する。

これにより、Scoreロジックを変更しても元データを再取得せず再計算できる構造を目指す。

---

## DECISION｜Direct企業・Agent・Platformを別マスターで管理する

統合版JobDDでは、以下を別マスターで管理する。

- companies：Direct応募先企業
- agencies：人材紹介会社
- platforms：求人媒体・転職プラットフォーム

求人そのものは jobs で管理し、

**求人 × 応募経路**

を application_routes で表現する。

同一求人について、

- Direct
- Agent A
- Agent B
- Platform

など複数経路が存在する場合も、それぞれ別のapplication_routeとして保持する。

JobDDの上位構造は、

**「会社比較」ではなく「求人に対して存在する応募経路比較」**

とする。

---

## DECISION｜Laravel向けDB v0.1の基本テーブル

卒業制作MVPでは、以下を基本構成とする。

### コア

- companies
- agencies
- platforms
- jobs
- application_routes

### JobDD独自データ

- agency_facts
- sources
- user_queries
- score_results
- interaction_logs

### 補助マスター

- occupation_tags
- industry_tags
- region_tags
- score_models

---

## DECISION｜元データ・根拠・Scoreを分離する

DBでは、

1. 調査で取得した事実
2. その根拠となるsource
3. JobDD Score算出結果

を分離して保存する。

特に agency_facts には、会社について確認できた事実を保存し、score_results には求職者ごとの算出結果を保存する。

Score結果には score_model_version を保持し、ロジック変更前後を追跡可能にする。

---

## DECISION｜AI調査結果には検証状態を持たせる

AIが公式サイト等から取得した情報は、原則として以下の状態を持つ。

- pending
- verified
- rejected

公的構造化情報等、信頼性が十分高いものは自動verifiedを許容する余地を持つが、MVPでは無理に完全自動化しない。

## HYPOTHESIS｜情報鮮度の初期ルール

初期案として、以下を再調査目安とする。

- 厚労省等の基本情報：180日
- 企業・紹介会社公式基本情報：90日
- 公開求人：30日

期限切れ情報は削除せず、再調査対象として扱う。

この期間は運用・検証結果を見て変更する。

---

## DECISION｜MVPで利用ログを最小限残す

卒業制作では、ユーザーの発言だけでなく実際の行動を観察するため、最低限以下をinteraction_logsへ保存する。

- results_viewed
- route_opened
- agency_opened
- evidence_opened
- route_selected
- agency_selected
- contact_clicked

これにより、

**「使いたいと言ったか」ではなく「実際に何を見て何を選んだか」**

を検証する。

---

## DECISION｜Slice 4 テストログ整理ルール

interaction_logsは、求職者インタビューで実際の行動を検証するためのデータとして扱う。
開発中の操作ログと実ユーザーの検証ログが混在しないよう、卒業制作MVPでは以下の運用ルールを採用する。

1. 開発中に生成されたinteraction_logsは、すべてテストログとして扱う。
2. 最初の求職者インタビュー直前に、既存のテスト用interaction_logsを一度全削除し、その時点を検証開始ラインとする。
3. 検証開始後の実ユーザーログは原則削除せず、生ログを保持する。
4. ページ再読み込み等による重複ログは保存を許容し、分析時にuser_query_id × event_type等で必要に応じて重複除外する。
5. 経路の選び直し等は削除せず、ユーザーの意思決定過程を示す行動として保持する。
6. 検証開始後に開発者が動作確認する場合は、専用のテスト用user_query_idを使用し、分析時に除外する。
7. 卒業制作MVPではis_testカラム等の追加実装は行わない。必要性が確認された場合に将来追加を検討する。

このルールの目的は、ログ管理機能を作り込むことではなく、

**求職者がJobDDの比較・Evidence・応募経路選択に実際にどう反応したかを、混入の少ない行動データとして検証できる状態を保つこと**

である。

### 現時点の整理

- FACT：interaction_logsへのresults_viewed / evidence_opened / route_opened / route_selected / contact_clickedの保存は実装・動作確認済み。
- DECISION：初回求職者インタビュー直前に開発テストログを全削除し、それ以降を検証ログとして扱う。
- DECISION：検証開始後の開発確認は専用user_query_idを使用し、分析時に除外する。
- DECISION：MVPではis_test等の専用カラムは追加しない。
- OPEN：将来の利用規模拡大時に、session識別、匿名ユーザー識別、is_test、ログ保持期間、プライバシー管理をどこまで実装するか。

---

- 業種・職種タグ体系の粒度
- 汎用Scoreの具体的な評価軸・配点

- 同一求人・同一法人・ブランド違いの重複統合ルール

卒業制作では、これらを完全に作り切ることより、求職者がJobDDのDecision Supportに価値を感じるかの検証を優先する。

# 37. 全国・全業種対応に向けた将来データ取得戦略（2026-08-31）

> **2026-09-02更新:** 本節は将来拡張アーキテクチャとして保持する。卒業制作の初期検証では全国・全職種化より機械設計・機電系でのPain検証を優先する。

## DECISION｜将来拡張時は事前収集DB＋オンデマンド補完のハイブリッド方式を基本候補とする

全国・全業種でJobDDの比較精度を高めるため、

**取得可能なデータは可能な範囲であらかじめDBへ蓄積し、ユーザー要求時は既存DBを優先参照し、不足分・期限切れ分だけAI/API等で補完する。**

毎回すべての人材サービス・求人・紹介会社をゼロからAI調査する方式にはしない。

### データ取得の3層

#### 第1層｜事前収集DB

事前に取得可能で、利用条件・更新コスト・法的整理の面で問題のない情報を蓄積する。

候補：

- 人材紹介会社の基本情報
- 職業紹介事業の許可情報
- 対応職種
- 対応地域
- 企業基本情報
- 公式採用ページURL
- Platform基本情報
- 公開求人
- 勤務地
- 年収帯
- 職種
- 求人更新日
- source URL
- 取得日時

取得手段の優先順位は原則として、

1. 公的・構造化データ
2. 公式API
3. 利用条件上取得可能な公開情報
4. 個別オンデマンド調査
5. AIによる構造化・事実抽出

とする。

#### 第2層｜検索時の差分取得

ユーザーの条件・求人URLを受け取った際は、まず保存済みDBを参照する。

以下の場合だけ再取得・追加取得する。

- factsが不足している
- 取得日時が古い
- 求人掲載状況の最新確認が必要
- 応募経路の存在確認が必要
- 既存情報のEvidenceが弱い

#### 第3層｜AI/API補完

構造化取得だけでは不足する箇所でAI/APIを利用する。

主な用途候補：

- 自然文入力の構造化
- 求人本文からの職種・業界・地域・年収等の抽出
- 企業公式ページからの検証可能なfacts抽出
- 同一求人候補の整理
- 応募経路候補の整理
- 根拠情報の要約・説明文生成

AIには原則として、

**「この会社は85点」**

のような判断値を直接保存させない。

保存するのは、

- 何を確認したか
- どのsourceで確認したか
- いつ取得したか
- どの程度確かな情報か

という再検証可能な事実と根拠とする。

ScoreはJobDD側の明示的ルールで算出する。

---

## DECISION｜DBを「Entity / Fact / Source / Score」に分離する

全国・全業種へ拡張するほど、元データと評価ロジックの分離が重要になる。

JobDDでは引き続き、

- Entity：企業・紹介会社・Platform・求人等の主体
- Fact：確認できた事実
- Source：根拠URL・取得日時・出典種別
- Score：求職者条件とFactから算出した結果

を分離して扱う。

これにより、Scoreロジックを変更しても、取得済みの元データを再利用して再計算できる状態を維持する。

---

## DECISION｜情報鮮度を比較品質の一部として扱う

DBに保存されていること自体を「現在も正しい」とはみなさない。

現時点の再調査目安は以下の初期案を継続する。

- 厚労省等の基本情報：180日
- 企業・紹介会社公式基本情報：90日
- 公開求人：30日

将来的には、

- fresh
- stale soon
- stale
- recheck required

等の鮮度状態を持つことを検討する。

古い情報は削除するのではなく、再調査対象として保持する。

---

## DECISION｜クローリング可否と利用可否を分けて判断する

技術的に取得可能であっても、無条件にクローリング対象とはしない。

本番運用へ進む際は、情報源ごとに少なくとも以下を確認する。

- robots.txt
- 利用規約
- API提供有無
- 商用利用可否
- 再配布可否
- アクセス頻度制限
- 保存可能なデータ範囲
- 更新・削除への対応

特に民間の求人媒体・転職Platformについては、

**「公開されている＝大量取得・保存・再利用してよい」**

とは扱わない。

取得できないデータを前提にJobDDの成立性を依存させない設計を優先する。

---

## HYPOTHESIS｜ハイブリッド方式によって全国・全業種対応の精度と経済性を両立できる

事前収集DBを持つことで、

- レスポンス速度の向上
- AI/API費用の削減
- 同じ情報を毎回再調査する重複コストの削減
- 回答の再現性向上
- Evidenceの安定化
- JobDD独自データ資産の蓄積

が期待できる。

一方で、完全な事前収集を目指すのではなく、

**頻繁に使われる・取得しやすい・汎用性が高い情報は先に蓄積し、ロングテール領域はオンデマンドで補完する**

ことで、全国・全業種対応を段階的に強化できる可能性がある。

この仮説は今後、取得コスト・APIコスト・検索速度・比較精度・ユーザー利用状況を計測して検証する。

ところまでを優先する。

# 38. クローリング / データ収集 将来技術スタック方針（2026-08-31）

> **2026-09-02更新:** 実検索・クローリング基盤の高度化は、求職者Pain検証後に優先順位を再判定する。

## DECISION｜Laravel本体とPythonクローラーを分離する

JobDD本体の技術スタックは引き続き、

- Laravel
- MySQL
- Blade
- Tailwind CSS
- 必要箇所のみJavaScript

を基本とする。

一方、全国・全業種へ向けた外部Webデータ取得・クローリングについては、Laravelだけで無理に完結させず、

**Laravel＝アプリ本体・比較・Score・ユーザー体験**
**Python＝外部情報収集・スクレイピング・データ整形**

という役割分担を基本方針とする。

---

## DECISION｜MVP段階のクローリング技術スタック

卒業制作MVP〜初期実運用では、以下を基本候補とする。

### Python側

- Python
- requests
- BeautifulSoup4
- lxml
- Playwright
- 必要に応じて pandas
- AI API

### 用途

#### requests + BeautifulSoup4

静的HTMLから取得可能な情報を収集する。

主な用途候補：

- 人材紹介会社公式サイト
- 企業公式採用ページ
- 公開求人ページ
- 公開されている構造化・半構造化情報

#### lxml

HTML / XML解析を高速・安定して行うための補助として利用する。

#### Playwright

JavaScriptによる描画・操作が必要なWebページについてのみ利用する。

すべての取得をブラウザ自動操作に寄せず、

**requests等で取得できない場合のフォールバック**

として扱う。

#### pandas

全国・全業種へデータ量が増えた場合に、

- CSV取り込み
- 重複除去
- 正規化
- 表記ゆれ整理
- 年収等の数値化
- 地域・職種・業界タグ付け前処理

等へ利用する。

---

## DECISION｜取得手段の優先順位

クローリング・外部データ取得は、原則として以下の順で利用する。

1. 公的・構造化データ
2. 公式API
3. requests等による取得可能な公開HTML
4. Playwright等によるブラウザ取得
5. AI APIによる不足情報の構造化・補完

AIを最初の取得手段にはしない。

**取得可能な事実を通常の方法で取得し、AIは構造化・整理・不足補完へ利用する。**

---

## DECISION｜AIはクローラーの代替ではなく、事実抽出・構造化に使う

AIの主な役割候補は、

- 自然文求人から職種・業界・地域・年収・経験等を抽出
- 企業公式ページ等から検証可能なfactsを抽出
- 同一求人候補を整理
- 応募経路候補を整理
- 根拠情報を求職者向けに説明・要約

とする。

AIへ、

「この会社は製造業に強いので85点」

のような判断を丸投げしない。

保存対象は原則として、

- raw_text
- extracted_fact
- source_url
- fetched_at
- verification_status
- その他Evidenceに必要な情報

とする。

ScoreはJobDD側の明示的ルールで算出する。

これは既存の、

- pending
- verified
- rejected
- Evidence Level
- Entity / Fact / Source / Score分離

という設計原則を継続するものである。

定期実行や差分更新については、Laravel Scheduler等からPython処理を呼び出す構成を候補とする。

概念例：

Laravel Scheduler
→ Python crawler
→ facts / sources をMySQLへ保存

- リトライ

- クロールキュー

- スケジューリング強化

### 移行目安の例

- 取得失敗・再試行を自動管理する必要がある

将来的には以下の構成を候補とする。

状態を目指す。

# 41. 2026-09-03 3経路TOP3比較方針

候補：

- 何が違うか
- 根拠は何か
- 注意点は何か

を比較できる方が、求職者が自分で判断しやすい可能性がある。

ただし、TOP3の有用性は未検証である。

1. クローリング・公開情報取得
2. Fact / SourceとしてDB蓄積
3. 3経路ごとの実データ差分を分析
4. 意思決定に有効な比較軸を抽出
5. Score / Evidence / TOP3表示へ反映

の順で再設計する。

# 43. 2026-09-04 Crawler取得戦略アップデート｜API非依存＋経路横断探索

## 背景

Direct / Agent / Platform の具体候補TOP3を実データから比較するため、各経路のデータ取得方法について検討した。

特に、外部APIを必須前提にするか、公開HTML・構造化データを中心に収集するかを整理した。

また、Direct求人については、全国企業の公式採用ページを最初から網羅する方式ではなく、Platform / Agent側で発見した求人・企業を起点に公式採用ページへ遡る方式を検討した。

---

## FACT｜現行Crawlerの基本技術で公開HTMLを取得できる状態にある

2026-09-04時点で、Python crawler環境では少なくとも以下を利用可能な状態としている。

- requests
- BeautifulSoup4
- lxml

JobDDの既存技術方針では、必要な場合のみPlaywrightをフォールバックとして利用し、AIは取得済み情報の構造化・事実抽出・不足補完に用いる。

ただし、個別媒体・紹介会社・企業公式サイトについて、JobDDで必要な全項目を安定して大量取得できることが確認済みという意味ではない。

---

## DECISION｜JobDD v1.0のCrawlerは外部APIを必須前提にしない

JobDD v1.0では、

**「APIが存在しなければ成立しないCrawler」にはしない。**

媒体・Agent・Directについては、取得条件・利用条件を確認したうえで、公開HTMLや構造化データから取得可能なFactをまず利用する。

APIは、以下のような明確な優位性がある場合に優先採用する。

- 公的・公式な構造化データを取得できる
- HTML取得より安定している
- 取得規約・商用利用条件が明確である
- 大量取得時の負荷・コストを抑えられる
- 更新検知・差分取得が容易になる
- HTML変更への耐性が高い

したがって、API利用そのものを実装目標にはしない。

---

## DECISION｜データ取得手段の優先順位を実運用ベースで整理する

原則として以下の優先順位を維持する。

1. 公的・構造化データ
2. 公式API
3. 公開HTML / JSON-LD等の構造化データ
4. requests + BeautifulSoup4 + lxml
5. 必要時のみPlaywright
6. AIによる事実抽出・構造化・不足補完

ただし、公式APIが存在していても、取得可能項目・料金・利用条件等を比較し、公開HTMLの方がJobDD v1.0に適している場合はHTML取得を採用できる。

重要なのは、

**「最も高度な取得方法を使うこと」ではなく、「JobDDの比較に必要なFactを、再検証可能な根拠付きで安定取得すること」**

とする。

---

- HTTP 200で取得成功
- `page=2` がリクエストへ反映された
- 1ページ目とは異なる求人群を取得できた
- `機械設計 × 兵庫県 × 正社員` の条件で、姫路・伊丹・神戸・尼崎・高砂・明石等の実在求人を確認

# 41. 2026-09-12｜3経路のDiscovery母集団・候補抽出・表示構造を整理

## DECISION｜JobDDは「巨大母集団をそのままランキングするサービス」にしない

JobDDでは、Direct / Agent / Platformそれぞれについて、母集団をそのまま全件表示・全件採点するのではなく、

**母集団 → Discovery → 活動・利用可能性確認 → 求職者条件とのFit評価 → Evidence確認 → 今回比較する代表候補**

という段階構造を採用する。

第1階層ではDirect / Agent / Platformの3経路を比較し、今回の条件で根拠が比較的強い経路を**「今回の有力候補」**として前面に出す。ただし、これはAIによる最終決定ではなく、他経路も確認可能なDecision Support表示とする。

第2階層では、選択・確認した経路内で**代表3候補程度**を比較する。

- Direct：直接応募可能な企業・求人候補
- Agent：人材紹介会社候補
- Platform：求人媒体・求人検索サービス候補

「代表3候補」は絶対順位・おすすめ確定を意味しない。比較可能な候補数へ絞るためのUXであり、最終判断は求職者本人が行う。

---

## DECISION｜Agentの母集団とDiscovery

Agentの母集団は、厚生労働省等の**職業紹介事業者に関する公的登録情報**を起点とする。

公的登録情報は、まず「登録されている／取り扱える」ことを示すRegistryとして扱い、会社の優劣や現在の活動量を直接意味するものとして扱わない。

Agentについては、以下を分離して管理する。

1. **Registry**：公的登録・許可・取扱職種・所在地等
2. **Activity**：現在、人材紹介事業として活動しているEvidenceが確認できるか
3. **Fit**：今回の求職者条件との適合
4. **Evidence**：上記判断を支える公開情報・公開求人・根拠URLの充実度

同一法人の複数事業所・支店が存在するため、公的データの行数をそのまま「会社数」とみなさず、許可番号・法人名・事業所情報を使って法人／拠点の関係を整理する。

### Activity Evidence候補

- 公式サイトに職業紹介サービスの説明がある
- 求職者登録導線がある
- 現在の公開求人が確認できる
- 対応職種・対応地域が明示されている
- 最近更新された求人・サービス情報が確認できる

### 重要原則

公開求人0件または求人未確認を、ただちに「悪いAgent」「活動していないAgent」とは判定しない。

非公開求人の存在や公開方針の違いがあるため、表示は

**「現在JobDDでは公開求人を確認できていない」**

等のEvidence状態として扱う。

また、公開求人件数の多さをそのままFit Scoreへ加点しない。大手・中小・専門特化型を会社規模や広告力で有利不利にせず、求職者との適合と確認できた根拠で比較する。

---

## DECISION｜Directの母集団とDiscovery

卒業制作MVPでは、全国全企業の完全企業名簿を先に構築することを目的にしない。

Directは、Agent求人・Platform求人等で発見した**求人企業をDiscovery母体**とし、企業名を起点に公式採用サイト・公式求人を逆引きする。

基本フロー：

**Agent / Platform等の実在求人 → 求人企業を発見 → 企業公式採用ページを探索 → 同一または近似求人の直接応募可否を確認 → `route_type=direct` としてEvidence化**

これは既存のDirect Reverse Lookup方針を継続する。

将来、PMFや必要性が確認された場合は企業DB・企業サイトクローリングの母集団を拡張する余地を残す。

---

## DECISION｜Platformの母集団とDiscovery

Platformは、主要な求人媒体・求人検索サービスのリストを母集団とする。

卒業制作MVPでは、媒体数を網羅することより、実在求人が取得でき、求職者条件との比較Evidenceとして利用できることを優先する。

現時点の候補・実装状況：

- Careerjet：実API取得・Importまで確認済み。主要Discovery候補
- Jooble：追加候補。日本向け実動確認はOPEN
- ハローワーク：公的Platformとして利用候補
- その他媒体：API、利用規約、robots、再利用条件を確認して段階追加

Platform評価も単純な総求人件数ランキングにはせず、**今回条件で確認できる求人Evidence、利用可能性、応募導線等**を比較材料とする。

---

## OPEN｜全国母集団の正確な件数

全国・全業種の公的データ母集団について、過去に大規模データを扱った経験はあるが、

- 法人数
- 許可事業者数
- 事業所数
- 求人数

を混同しないよう、全国展開前にデータ定義と正確な件数を再確認する。

「件数が巨大であること」自体をMVP価値とはしない。

# 42. 2026-09-12｜実在Agent求人パイプラインと職種正規化

## FACT｜メイテックネクストの実在求人取得パイプラインが動作

2026-09時点で、メイテックネクストについて、

**公式求人検索 → Python crawler → JSON → Laravel Importer → MySQL → Agent Evidence表示**

のVertical Sliceが動作している。

## FACT｜リクルートエージェントの実在求人取得パイプラインが動作

リクルートエージェントについて、兵庫県×「機械設計」検索を起点に、一覧ページのcursor pagination、求人詳細JSON-LD、HTML内部データからの想定年収取得まで実装した。

- discovered jobs：886件
- success：886件
- failed：0件
- 想定年収取得：886 / 886件

を確認した。

Importerでは、

- Import対象：884件
- 新規求人：871件
- 既存求人と統合：13件

- errors：0件

となった。

公開求人の想定年収は、JSON-LDの月給を12倍する推定ではなく、HTML内部に明示された「想定年収」を優先してFACTとして保存する。

## FACT｜検索キーワードと実際の職種は同一ではない

リクルートエージェントで「機械設計」を検索した結果には、AI・データサイエンティスト、社内システムエンジニア等、機械設計そのものではない求人も含まれることを確認した。

したがって、

**検索キーワード = 職種FACT**

とは扱わない。

---

## DECISION｜共通OccupationNormalizerを採用

検索キーワード由来の固定職種をやめ、求人タイトルを最優先、求人本文を補助として、JobDD共通職種へ正規化する `OccupationNormalizer` を導入した。

初期カテゴリ候補：

- 機械設計
- 電気設計
- 生産技術
- 品質保証
- プラントエンジニア
- 施工管理
- ソフトウェア・IT
- その他技術職
- 判定不能（null）

判定できない求人を無理に既存カテゴリへ押し込まず、nullを許容する。

リクルートエージェント再Import後、例として

**「AI・データサイエンティスト（機械学習、深層学習等）／社内システムエンジニア」 → 「ソフトウェア・IT」**

へ正規化できることを確認した。

また、Recruit経由求人のうち `occupation=機械設計` は677件となり、兵庫県×機械設計×希望年収400万円以上の画面Evidenceは631件となった。

### HYPOTHESIS

辞書＋ルールベースのOccupationNormalizerで、卒業制作MVPに必要な職種Evidence精度を十分改善できる可能性がある。

### OPEN

- 分類カテゴリの正式粒度
- 複合職種の扱い
- タイトルと本文が矛盾する場合の優先順位
- Meitec / Ties / Platformへの共通適用
- 誤分類率の測定方法
- AI補助分類を導入する必要性

# 43. 2026-09-12｜開発方法を「対話学習優先」から「仕様合意＋高速実装」へ更新

## それまでのDECISION

JobDD v1.0までは、Laravel / MVC構造を理解しブラックボックス化を避けるため、ChatGPTとの対話で一歩ずつ実装し、Codex等による大規模一括実装は原則使わない方針だった。

## FACT

Vertical Slice、Controller / Service / Model / Blade、Crawler → JSON → Importer → DB → UI等を対話形式で実装する過程を通じ、Laravel構成とJobDDのデータフローについて一定の理解が進んだ。

## DECISION｜高速開発モードを解禁する

2026-09-12以降、9/19までの実用MVP完成を優先し、Codex等を使った

- 複数ファイル一括変更
- CRUD・Importer・Crawler共通化
- 重複コード整理
- テスト追加
- リファクタリング
- UI実装

等の高速実装を積極的に利用する。

基本フローは、

1. JobDD_Master / Decision Logと照合する
2. ChatGPTとの壁打ちで仕様・仮説・優先順位を握る
3. Codex等へ実装タスクをまとめて渡す
4. git diff / tests / 画面で変更を確認する
5. 重要な事業ロジックは人間側でもレビューする

とする。

### Codexへ丸投げしない領域

以下は事業仮説そのものに関わるため、実装前に仕様を明示する。

- Direct / Agent / Platformの基本思想
- Score / Fitロジック
- Evidenceの意味
- Activity / Registryの扱い
- 求職者Painに関わるUX
- DBの根本設計変更

この更新は、以前の「v1.0まではCodexを原則使わない」という開発方針を**明示的に置き換える最新DECISION**とする。
